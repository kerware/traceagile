# ADR-0020 — Exécution automatisée : jeton émis par le serveur, runs, webhooks, import, tests instables

**Statut** : acceptée (lot 7)

**Contexte.** Les §8.5 et §10 décrivent le lancement de tests automatisés sur un serveur d'exécution
distant, le contrat d'API, le simulateur, l'import de rapports et la détection des tests instables. Le
demandeur a ajouté une exigence : **la connexion avec le serveur est authentifiée par un jeton de
sécurité généré par le serveur**. Pour chaque point ouvert, l'option la plus simple a été retenue (§16.1-5).

**Décisions.**

| Sujet | Décision |
| --- | --- |
| Jeton émis par le serveur | Le serveur d'exécution expose `POST /api/v1/tokens`, réservé à **son** administrateur (HTTP Basic). La réponse contient un jeton d'accès (`ets_…`, 256 bits aléatoires) et un **secret de signature des webhooks** (`whs_…`). Le serveur ne garde que l'empreinte SHA-256 du jeton. Il peut lister ses jetons (sans secret) et les révoquer (`DELETE /tokens/{id}`). Toutes ses autres routes, sauf `/health`, exigent `Authorization: Bearer <jeton>` : un jeton inconnu ou révoqué donne 401. |
| Appairage dans TraceAgile | Administration système, `POST /execution-servers/{id}/pair`, de deux façons : (1) TraceAgile demande le jeton au serveur avec les identifiants de l'administrateur du serveur, qui **ne sont pas conservés** ; (2) l'administrateur saisit le jeton et le secret émis sur le serveur. TraceAgile chiffre jeton et secret au repos en AES-256-GCM (clé `TRACEAGILE_ENCRYPTION_KEY`) et ne les renvoie jamais : l'API n'expose qu'une empreinte (4 derniers caractères) et l'identifiant du jeton. Changer l'URL du serveur efface le jeton. |
| Santé du serveur | Heartbeat toutes les 60 s (`/health` et `/capabilities`) : `ONLINE`, `OFFLINE` (injoignable) ou `UNAUTHORIZED` (jeton refusé : il faut un nouvel appairage). Les capacités (techniques, frameworks, environnements, agents) viennent du serveur ; un run n'est accepté que si le serveur sait exécuter toutes les techniques des tests (`RUN_TECHNIQUE_UNSUPPORTED`). Un serveur qui a reçu des runs ne se supprime pas, il se désactive. |
| Run et tentatives | `POST /campaigns/{key}/runs` (droit `AUTOMATED_RUN_LAUNCH` : développeur, administrateur) crée un run `QUEUED` avec l'environnement et le build de la campagne, et une tentative `NOT_RUN` par test, liée au run. Un test déjà en cours ou en attente est refusé (`RUN_ITEM_BUSY`). Le job est ensuite envoyé **hors transaction**, car les webhooks peuvent arriver avant la réponse. Le run passe `DISPATCHED`, ou `FAILED` si le serveur est injoignable ou refuse le jeton ; dans ce cas, ses tentatives passent `ERROR`. |
| Webhooks (§10.4) | `POST /api/v1/execution-callbacks` est sans JWT. La signature HMAC-SHA256 du corps brut est vérifiée avec le secret du serveur du run (401 sinon) ; un `runId` inconnu donne 404 ; un `eventId` déjà traité est ignoré (table `processed_webhook_events`). Le `runId` n'étant unique que par projet, le run retenu est celui dont la signature correspond. Un événement reçu après la fin du run (annulé, expiré, terminé) est ignoré. JOB_FINISHED clôt le run ; les tentatives encore ouvertes passent `SKIPPED`. JOB_ERROR met le run en échec et ses tentatives ouvertes en `ERROR`. Le message d'échec et la trace sont conservés dans le commentaire de la tentative, tronqué à 2000 caractères. |
| Temps réel (F-EXE-07) | Flux Server-Sent Events par run (`/runs/{key}/events`) et par campagne (`/campaigns/{key}/run-events`). Chaque changement **validé** (après commit) envoie un événement `run` minimal ; le navigateur relit alors le run. Le navigateur lit le flux avec `fetch`, pour envoyer le jeton Bearer, et se reconnecte au bout de 3 s. Les journaux sont lus sur le serveur à la demande (`/runs/{key}/logs`). |
| Annulation, relance (F-EXE-08, F-EXE-09) | L'annulation est demandée au serveur au mieux (une erreur réseau n'empêche pas l'annulation locale) ; les tentatives ouvertes passent `SKIPPED`. « Relancer les échecs » crée un **nouveau** run (`rerunOf`) avec les tests `FAILED` ou `ERROR` du run terminé. |
| Polling et timeout | Une tâche planifiée, chaque minute, cherche les runs sans événement depuis `timeoutMinutes` + 5 min. Elle relit d'abord le job (`GET /jobs/{id}`) et applique les événements manqués, puis, s'il reste en retard, le passe `TIMEOUT` ; ses tentatives ouvertes passent `ERROR`. |
| Client HTTP | `RestClient` sur `HttpURLConnection`, avec des délais courts. Pour les lectures et la soumission, qui est idempotente par `runId`, trois essais sur erreur réseau ou 5xx. `X-Correlation-Id` est propagé (NF-15). Resilience4j (§11.1) n'est pas utilisé : ces nouvelles tentatives simples suffisent au prototype. |
| Import (F-EXE-10) | `POST /campaigns/{key}/imports` (multipart, `format`, `apply`, `createUnknown`). Un résultat est rapproché d'un test automatisé par son `testIdentifier`, en essayant plusieurs identifiants candidats : JUnit « paquet.Classe#méthode », « Classe#méthode », « méthode » ; Cucumber et Robot, le nom du scénario ou du test ; Playwright, le chemin « fichier › describe › titre ». À défaut, il est rapproché par un tag d'exigence (`@REQ-n`), si cette exigence n'a qu'un test automatisé. Sans `apply`, c'est un aperçu. À l'application, les inconnus peuvent être créés : technique déduite du format (UNIT, BDD, KEYWORD, UI), test lié aux exigences de ses tags. Les tests absents de la campagne y sont ajoutés, et chaque résultat devient une tentative « automatisée » (`executedBy` : import). Le XML est lu sans DTD ni entité externe. |
| Tests instables (F-EXE-11) | Sur les 10 dernières exécutions terminées d'un test, regroupées par build de campagne, au moins deux alternances entre réussite et échec (`FAILED` ou `ERROR`) sur un même build. Les autres statuts sont ignorés. L'indicateur `flaky` est recalculé après chaque résultat automatisé (webhook, polling, import) et affiché sur le test, la campagne et le run. Le signalement dans le bilan arrive au lot 8. |
| Simulateur (§10.5) | Module `mock-execution-server` (port 8090) qui implémente le contrat `docs/execution-server-api.yaml`, y compris l'émission des jetons. Les résultats sont tirés au sort selon `passRate` (0,8) et `errorRate` (0,05), avec un délai de 1 à 3 s par test. Un identifiant contenant `@fail` échoue toujours ; `@flaky` alterne d'un job à l'autre. Les jetons et les jobs sont en mémoire : après un redémarrage du simulateur, le heartbeat passe `UNAUTHORIZED` et la démo appaire de nouveau. |
| Démonstration (§15.1) | Serveur « Simulateur » déclaré au démarrage. Il est appairé dès qu'il répond, puis toutes les 30 s s'il le faut, avec les identifiants d'administration du simulateur configurés dans Docker Compose. CMP-2 reçoit 3 runs passés sur ses premiers tests automatisés ; deux d'entre eux échouent au deuxième run seulement et sont donc **instables**. |
